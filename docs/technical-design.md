# Windows 桌面隐水印拍屏溯源技术原理说明

## 1. 技术目标

目标是在 Windows 桌面上叠加肉眼低感知的隐水印，使手机拍屏照片、斜拍照片、局部屏幕照片在上传后仍可恢复出水印载荷，并据此完成泄露溯源。

核心诉求不是“让人看见一个标记”，而是让屏幕画面中长期存在一个可被算法检测的弱信号。这个弱信号需要同时满足：

1. 视觉可感知度低，不明显干扰桌面使用。
2. 拍屏后可恢复，能抵抗透视、缩放、模糊、曝光、压缩、摩尔纹。
3. 支持局部屏幕，只拍到一部分画面也能解出。
4. 可盲检测，解码端不依赖原始桌面内容。
5. 可溯源，解出的短载荷能映射到人员、设备、会话。

## 2. 当前算法设计原则

当前实现采用“全屏平铺、低频调制、盲检测恢复”的设计。

水印不是一个集中式可见标记，而是一个分布在桌面像素中的弱信号。每个水印块都独立携带完整载荷，多个水印块在解码时可以共同投票。这样即使图片只覆盖部分屏幕，也仍有机会恢复出同一个 payload。

算法设计遵循五个原则：

1. **低频优先**：使用二维低频纹理，提高对手机拍摄、显示器采样、模糊和压缩的穿透能力。
2. **全屏冗余**：同一载荷在整个桌面平铺重复，支持局部屏幕溯源。
3. **密钥驱动**：频率对、相位和同步结构由 secret 派生，避免固定公开模板。
4. **统计恢复**：解码端不依赖原始桌面，通过匹配滤波、纠错和多块投票恢复载荷。
5. **可信判定**：输出 payload 之前同时检查纠错次数、图案置信度、同步强度和登记信息。

## 3. 拍屏链路的信号退化模型

屏幕上的水印不是直接被算法读取，而是经过一条复杂链路：

```text
桌面像素
  -> 屏幕显示子像素
  -> 手机镜头成像
  -> 传感器采样
  -> 自动曝光/白平衡/锐化
  -> JPEG/HEIC 压缩
  -> 上传图片
  -> 算法解码
```

这条链路会产生几类主要退化：

1. 几何退化：旋转、缩放、透视、屏幕边缘裁切。
2. 光学退化：失焦、运动模糊、镜头畸变。
3. 采样退化：屏幕像素网格与相机像素网格叠加产生摩尔纹。
4. 亮度退化：自动曝光、局部反光、屏幕亮度变化。
5. 压缩退化：JPEG 块效应、高频细节损失。
6. 背景干扰：桌面内容本身就是强纹理噪声。

因此，拍屏水印不能依赖细小边缘，也不能依赖单个局部图形。它应该尽量使用低频、周期性、可累积的信号，并通过冗余和统计检测恢复。

## 4. 当前推荐方案：低频 FSK 分布式水印

当前推荐方案是低频 FSK，也就是频率键控水印。它把每一位信息编码成一对低频二维余弦纹理中的一个：

```text
bit = 0 -> 使用频率 f0
bit = 1 -> 使用频率 f1
```

每一个水印块都携带完整 payload。水印块再平铺到整个桌面：

```text
payload
  -> 纠错编码
  -> 频率对选择
  -> 低频二维纹理
  -> 全屏平铺
```

这种设计的关键优势是：

1. 低频纹理更容易穿过手机拍摄、显示器采样、缩放和压缩链路。
2. 频率响应可以在噪声背景下通过匹配滤波累积出来。
3. 每个水印块都包含完整 payload，天然支持局部屏幕溯源。
4. 多个水印块可以投票或聚合，提升低信噪比下的恢复概率。
5. 加入同步频率后，可判断图像是否真的包含目标水印结构。

## 5. 载荷、纠错与短 token 设计

水印不直接编码姓名、账号、设备名等长信息，而是编码一个短 token。当前原型使用 32 bit payload，表现为 8 位十六进制字符串，例如：

```text
1a2b3c4e
```

推荐业务上这样使用：

```text
payload token -> 用户 / 设备 / 会话 / 时间窗口 / 策略版本
```

短 token 的好处是信号负担小，水印更稳。真实身份信息留在服务端登记表里，既便于轮换，也避免泄露图片中直接携带敏感身份。

为了抵抗拍屏噪声，payload 先经过纠错编码。当前原理是把 32 bit 拆成多个小块，每个小块加入冗余校验位，解码时允许一定数量的 bit 被纠正。

这里要注意一个重要工程事实：纠错能提高恢复率，但也会带来伪码风险。噪声很大时，解码器可能仍然“凑出”一个合法 payload。因此生产系统不能只看是否输出 payload，还要看：

1. 纠错次数是否很低。
2. 水印模式匹配度是否足够高。
3. 同步信号是否足够强。
4. payload 是否在登记表中存在。
5. 是否通过额外 CRC 或签名校验。

## 6. 为什么要全屏平铺

全屏平铺是拍屏溯源的核心设计之一。

如果只在屏幕角落或中心放一个水印，用户只需要避开那个区域，或者照片只拍到局部，就可能无法溯源。全屏平铺则让任意区域都包含水印信息。

理想情况下，一张照片只要覆盖若干个水印块，就可以恢复 payload：

```text
完整屏幕照片 -> 多个 tile 聚合，稳定性最好
半屏照片     -> 仍有多个 tile，可恢复
局部照片     -> 只要有足够 tile，仍可尝试
极小裁切     -> tile 数不足，置信度下降
```

全屏平铺还有一个好处：桌面背景对不同区域的干扰不同。多个 tile 聚合后，背景噪声趋向相互抵消，而水印信号因同源重复会增强。这是扩频/重复编码类水印的基本收益。

## 7. 为什么要做屏幕矫正

手机拍屏通常不是正对屏幕。原图中的屏幕是一个四边形，而不是标准矩形。如果直接在原图上切水印块，会出现两个问题：

1. tile 尺寸不再恒定。
2. tile 网格方向和原始桌面不一致。

因此必须先做屏幕几何矫正：

```text
照片中的屏幕四边形
  -> 找到四个角点
  -> 透视变换
  -> 拉正为矩形屏幕图
```

矫正之后，水印块重新接近规则网格，才能按 tile 周期做频率匹配。

当前系统支持两种角点来源：

1. 自动识别屏幕边框。
2. 手动点击四角。

手动点位已经增加几何排序保护。即使点击顺序错误，服务端也会按几何位置重排为：

```text
左上、右上、右下、左下
```

这可以避免第三点、第四点反掉时造成的交叉透视变换。

## 8. 为什么 tile 尺寸不能固定为 256

桌面水印生成时的 tile size 可以是 256 像素，但拍屏照片被透视矫正后，图像尺寸往往不等于原始桌面分辨率。此时水印周期也会被缩放。

例如原始桌面高度约 1200，矫正后高度约 1377，则原本 256 像素的水印块会变成约：

```text
256 * 1377 / 1200 ≈ 293
```

如果仍按 256 切块，就会切错周期。切错周期时，频率匹配器仍可能输出一个 payload，但这个 payload 可能是伪码。

因此拍屏溯源必须做 tile 尺寸估计：

```text
矫正后屏幕尺寸
  -> 估计缩放比例
  -> 得到候选 tile_px
  -> 对多个 tile_px 分别解码
  -> 选择最可信结果
```

最近测试中，`test9.jpg` 的正确 tile 尺寸就是 293，而不是 256。这也是 Web 端最初误码的一个关键原因。

## 9. 同步与偏移搜索

即使 tile 尺寸估对了，水印网格也不一定刚好从矫正图左上角开始。解码器还需要找到 tile 网格的偏移：

```text
tile_px = 293
best_offset = 0,0 或其他偏移
```

当前原理是两步：

1. 先利用同步频率做相位相关，得到可能的偏移候选。
2. 再在候选附近和规则网格上扫描，选择综合得分最高的偏移。

偏移同步的质量会体现在 `sync_confidence` 和 `best_offset` 上。正确矫正、正确 tile 尺寸时，同步置信度通常明显更高，纠错次数也更低。

## 10. 解码置信度与误报控制

拍屏水印系统必须重视误报。一个算法“总能输出 payload”并不等于“溯源成功”。在强噪声下，任何二进制解码器都可能输出一个看似合法的结果。

当前需要综合判断以下指标：

```text
correctedCodewords：纠错次数，越低越好
patternConfidence：频率模式匹配度，越高越好
bitConfidence：bit 判决稳定性
syncConfidence：同步频率强度
tilesUsed：参与聚合的水印块数量
payloadRegistered：payload 是否已登记
```

经验上：

```text
可信结果：
correctedCodewords = 0
patternConfidence >= 0.95
syncConfidence >= 1.0
payload 已登记

风险结果：
correctedCodewords >= 6
patternConfidence 约 0.6-0.8
syncConfidence 很低
payload 未登记
```

最近出现的错误结果：

```text
payload=368848e6
corrected=9
pattern_confidence=0.7561
sync_confidence=0.3751
```

它虽然输出了 payload，但指标已经明显不健康。生产系统应把这类结果标为低置信度候选，而不是直接作为溯源结论。

进一步降低误报的建议是增加 CRC 或签名：

```text
payload = session_id + CRC/signature
```

解码后只有 CRC 或签名通过，才允许进入可信溯源链路。

## 11. Web 溯源服务的技术链路

Web 服务本质上是把上述算法链路产品化，形成可操作、可审计的溯源流程：

```text
上传拍屏照片
  -> 自动或手动获得屏幕四角
  -> 角点几何排序
  -> 透视矫正
  -> 自动估计 tile 尺寸
  -> 搜索 tile 偏移
  -> 聚合多个 tile 的频率响应
  -> 恢复 payload
  -> 查询登记信息
  -> 保存本次溯源记录
  -> 更新成功率统计
```

Web 页面展示的“记录编号”不是水印内容，而是服务端对本次解码尝试的流水号。真正用于溯源的是“水印载荷”，再通过登记表映射到对象。

记录系统应保存的不只是最终 payload，还应保存置信度、纠错次数、角点、矫正尺寸、tile 尺寸、偏移等证据。这样后续可以复核误码、统计成功率，并持续优化阈值。

## 12. 当前验证结论

当前原型已经证明以下路线可行：

```text
低频 FSK 水印
  + 全屏平铺
  + 拍屏透视矫正
  + 自动 tile 尺寸估计
  + 多 tile 聚合
  + 纠错和置信度判断
```

`test9.jpg` 的命令行自动溯源结果：

```text
status=ok
payload=1a2b3c4e
corrected_codewords=0
bit_confidence=1.0213
sync_confidence=1.6077
pattern_confidence=0.9763
tiles_used=28
tile_px=293
best_offset=0,0
```

同一图片在 Web 服务端也已验证：

```text
自动溯源：payload=1a2b3c4e, corrected=0, tile=293
手动点位自动重排后：payload=1a2b3c4e, corrected=0, tile=293
```

此前 Web 手动选点误码的直接原因是：

```text
第三、第四个点顺序反了
  -> 透视矫正交叉
  -> tile 网格被破坏
  -> 输出伪 payload
```

修复方式：

```text
手动四点先做几何排序，再透视矫正
```

## 13. 当前方案边界

当前原型仍有边界：

1. 对极小局部裁切，如果完整 tile 数不足，解码会明显变差。
2. 对强反光、严重失焦、严重过曝场景，低频信号也可能被淹没。
3. 当前纠错能力有限，高噪声下仍可能输出伪 payload。
4. 自动屏幕检测依赖屏幕边框可见，极端裁切时需要手动选点。
5. 自适应水印需要跟随桌面内容刷新；如果刷新间隔过长，窗口剧烈变化后仍可能出现旧桌面残影干扰。
6. 当前阈值还需要真实手机、屏幕、角度、光照测试集来标定。

## 14. 工业化增强方向

如果继续推进到生产级，建议重点增强以下能力：

1. 加入 CRC 或签名，显著降低伪码作为可信结果的概率。
2. 将 Hamming 纠错升级为 BCH、Reed-Solomon 或 LDPC。
3. 建立真实拍屏测试集，覆盖手机型号、屏幕型号、角度、距离、亮度、压缩质量。
4. 用测试集标定 `patternConfidence`、`syncConfidence`、`correctedCodewords` 阈值。
5. payload 按人员、设备、会话、时间窗口滚动生成，避免长期复用。
6. 溯源记录中保存图片哈希、算法版本、参数版本、操作者、时间戳。
7. 解码服务异步化，对困难样本启动更密集的 tile range 和 offset scan。
8. 对上传图做曝光归一化、去摩尔纹、局部对比增强和边缘外扩裁剪。
9. 前端区分“可信命中”“低置信候选”“未登记候选”，避免误用调试 payload。
10. 周期性更新自适应覆盖层，使水印残差跟随桌面内容变化；当前 `--camera-mode` 默认每 2 秒刷新一次。

## 15. 附：当前原型使用入口

启动桌面水印：

```powershell
python -m screen_watermark.overlay --payload 1a2b3c4e --camera-mode
```

`--camera-mode` 默认启用自适应覆盖层周期刷新，避免窗口切换后旧桌面内容残留到水印层；如需关闭可使用 `--refresh-interval 0`。

启动 Web 溯源服务：

```powershell
python -m screen_watermark.trace_server --port 8766
```

打开：

```text
http://127.0.0.1:8766
```

命令行离线验证：

```powershell
python -m screen_watermark.decode test9.jpg --camera-mode --auto-screen
```
